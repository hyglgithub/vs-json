# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev         # next dev — but see port note below
npm run build       # next build
npm run start       # next start
npm run typecheck   # tsc --noEmit — this is the only static check; there is no lint or test runner
npm run e2e         # node e2e.cjs — needs the dev server already up
```

There is **no test framework, no ESLint, and no Prettier** in this project. `npm run typecheck` is the whole quality gate.

**CI** (`.github/workflows/ci.yml`) runs exactly those two gates — `npm run typecheck` and `npm run build` — on push and PR to `main`, on Node 22. **`e2e.cjs` is deliberately *not* in it**: it needs a live dev server plus a headless browser, and that timing is far more fragile than the two gates. On a brand-new public repo a red badge is worse than no coverage. If you add it, give it its own job rather than bolting it onto `check`.

**`pages.yml`** is separate and does a *different* build: it sets `GITHUB_PAGES=1`, so `next.config.ts` turns on `output: 'export'` and `basePath: '/vs-json'`, then uploads `out/` to GitHub Pages. The two `build` steps are not redundant — `ci.yml` validates the ordinary production build (also what Vercel does), `pages.yml` validates the static export. Both run on a push to `main`.

**Port 3112:** `e2e.cjs` defaults to the dev server on **3112**, so start it as `npx next dev -p 3112` when you want to drive the app or run the e2e script. The `npm run dev` script has no `-p` flag. If 3112 is taken by something else, start the app wherever and point the harness at it with `APP_URL=http://localhost:<port>/ npm run e2e`.

**`e2e.cjs`** is an ad-hoc CDP harness, not a real test suite:
- It is **portable now** — `ws` is a devDependency, the browser is auto-detected per platform (Chrome, falling back to Edge), and the temp profile goes under `os.tmpdir()`. `CHROME_PATH` / `APP_URL` / `CDP_PORT` override the three. It used to require `ws` from an absolute path on one machine's Desktop and launch Chrome from a hardcoded `C:/Program Files/...`.
- It clicks buttons by matching their **Chinese `textContent`** (`格式化`, `压缩`, `Unicode`, …), `console.log`s the textarea value after each step, then runs 6 assertions and exits non-zero on failure.
- It waits for React **hydration** before injecting text (polling for `__reactFiber$`/`__reactProps$` on `.editor-front`) and clears the field before setting it, because React's value tracker otherwise adopts the injected text as its baseline and swallows the `input` event. Both waits look like dead time; they are not — without them the harness silently tests an empty editor.
- Run it with the dev server already up: `npm run e2e`.
- The CDP HTTP endpoint is deliberately pinned to `127.0.0.1` rather than `localhost`: on Windows, `localhost` can resolve to `::1` first while Chrome's debugging port listens on IPv4 only, which reads as "connection refused".

## Architecture

A single-page **client-side** JSON viewer/formatter. **There is no server call and no network path of any kind** — an earlier build had an `/api/organize` route proxying an LLM "organize this JSON" request, and it was removed at the user's request ("项目无需任何ai功能"). Nothing replaced it. All UI text, code comments, and error messages are **Chinese** (`<html lang="zh-CN">`).

**Next.js 15 App Router, React 19, TypeScript `strict: true`.** No Tailwind, no CSS modules, no state library.

- `app/layout.tsx` — server component; sets metadata and imports `./globals.css`. The tab reads `title` (`VS Json - 自用json格式化工具`) and **only** `title`: a browser never renders `meta description` in the tab, which is worth remembering because it was asked for once already. The description goes to three other places instead — search snippets, the share-link preview (`openGraph` / `twitter`), and bookmarks. `TAGLINE` / `TITLE` / `DESCRIPTION` are derived from one string so the title's suffix cannot drift from the description's opening. Keep the title short: it is also the search-result and share-card heading, and it truncates in a crowded tab strip.
- `app/icon.png` (512²) and `app/apple-icon.png` (180²) — the tab icon and the iOS home-screen icon, picked up by App Router's **file convention** (no `icons` field in the metadata, no `<link>` tag written by hand — the convention also prepends `basePath` for you). The design is a dark `{}` glyph on an `--accent` tile: a coloured tile is far more legible at 16px than a dark one, and the two braces' stems are 32/64 apart because an earlier version drawn from real brace curvature left only 10/64 between them and the two halves fused into one blob at favicon size. The vector source is `docs/icon.svg`; regenerate the PNGs by rendering it in a browser at the target size (they were rendered at 1× with a transparent background).
  - **There must be only ONE file whose base name is `icon`.** The convention resolves a *single* file per base name, picking by extension priority with `png` ahead of `svg` — so `icon.svg` next to `icon.png` is **silently dropped**: the file still gets copied into `out/`, but no `<link>` is emitted for it, and the SVG looks like it works while doing nothing. (This is what `docs/icon.svg` avoids by living outside `app/`.) If you genuinely need two formats, the escape hatch is the numeric-suffix form (`icon0.png` / `icon1.svg`), which introduces its own "which one does the browser pick" ambiguity — not worth it here.
  - **The icon was SVG-only and that was a real bug**, not a style choice: browsers that don't implement SVG favicons showed *no icon at all* rather than falling back. The 512² PNG is downscaled to 16px perfectly well and is supported everywhere, so it is the safe single choice. If you redraw, **render it at 16px and look at it** before committing — that is the only size that matters and the only way the brace fusion shows up.
- `app/page.tsx` — a `"use client"` module whose whole job is `dynamic(() => import("../components/JsonTool"), { ssr: false })`. **The `ssr: false` is load-bearing** — it exists so that stored preferences are read *before* the first render and the first paint is already correct; see the prefs entry under Conventions. `<JsonTool />` is the entire page.
- `components/JsonTool.tsx` — the only module holding **application state** (~770 lines: state, effects, handlers, then the topbar/toolbar/activity-bar shell). The right-hand panels are *not* here any more; they live in `components/panels/` and are selected through a **registry**, not a ternary chain:
  ```tsx
  const panels: { id: PanelId; tip: string; icon: ReactNode; content: ReactNode }[] = [ … ];
  ```
  The activity bar's buttons and the open panel's body both derive from that one array, so the tab order and the panel set cannot drift apart, and `rightPanel` is `"none" | PanelId`. The order is **树形视图 / 保存记录 / 帮助 / 设置** (帮助 was swapped ahead of 设置 at the user's request; AI 整理 sat between 保存记录 and 帮助 until the feature was removed). **Adding a panel is now: write a component under `components/panels/`, append one entry to `panels`.** It used to mean inserting a branch *before* the 帮助 `else` fallback of a four-arm ternary, which is exactly the trap the registry removes — do not reintroduce a fallback arm.
- `components/` (the rest) — presentational components, one concern each. `Editor.tsx` is the four-layer editor; `JsonNode.tsx` is one tree row (recursive); `Highlight.tsx` wraps query hits in `<mark>`; `Select.tsx` is the settings dropdown; `Toasts.tsx` is the message stack; `Hint.tsx` is the one-sentence empty state; `panels/` holds `TreePanel` / `HistoryPanel` / `SettingsPanel` / `HelpPanel`, each rendering a whole `.pane` including its own `.pane-head`. **They are controlled: they hold no application state and take everything through props.** `Select` is the one exception and it is a deliberate one — `open` / `hi` / `pos` are the popup's own UI state, not the app's. `Editor` is also the one place where **refs are created by the parent and passed down**, because `JsonTool` has other effects that must read the same `editorRef` / `marksRef` / `numsRef` objects (search scrolling, the folded scroll hand-off). Do not move those refs into `Editor`.
- `lib/` — pure helpers, six flat modules. **They contain no React and no component state, and must stay that way.** The seams are two: **`lib/` may not see a `useState`** (if a function needs one, it belongs in a component), and **a component may not own application state** (it goes in `JsonTool.tsx` and comes down as props). Splitting state into a Context/store was considered and rejected: `expanded` / `query` / `activeIndex` genuinely belong to one screen.
  - `lib/prefs.ts` — the preference bag: `PREFS_KEY`, `PREFS_V`, the `Prefs` type and `SortMode`, `SETTINGS_DEFAULTS`, the option lists (`INDENT_STEPS` / `FONT_SIZES` / `SIDE_MIN` / `SIDE_MAX`), `clampSide`, and `loadPrefs` / `savePrefs`. Pure and React-free; the only module that touches `jsontool.prefs`. See the preferences entry under Conventions.
  - `lib/constants.ts` — `NL1` / `BS`, `TOAST_MS` / `TOAST_OUT_MS` / `TOAST_MAX`, the `ToastKind` type, `HIST_KEY` / `HIST_MAX` / `HIST_MAX_CHARS`, the `HistoryEntry` type, `SAMPLE`. `SAMPLE` is not sample *data* — it is the tutorial, in full (see the `SAMPLE` entry under Conventions).
  - `lib/json.ts` — the `JsonValue` / `Match` / `FoldRange` types, `isObject` / `joinKey` / `joinIndex` / `valueClass` / `computeStats` / `collectPaths` / `deepSort` / `findMatches` / `foldRanges`. `escapeKey` is deliberately **not** exported — `joinKey` is its only caller. `foldRanges` is a string-aware bracket scan returning `Map<openLine, {closeLine, closeCol}>` for multi-line blocks; it scans the *text* rather than walking the parsed value because the AST carries no line numbers, and folding is a per-line operation. It must skip brackets inside string literals (`{"a": "[{"}`), hence the escape state machine.
  - `lib/text.ts` — `escapeUnicode` / `unescapeUnicode` (a matched pair — keep them adjacent), `escapeText` / `unescapeText`, `reformatJson`.
  - `lib/format.ts` — `fmtTime` / `fmtRel` / `fmtBytes` / `histPreview`.
  - `lib/help.ts` — the help/tutorial copy: `HELP_SECTIONS` (the manual, one entry per topic) and `EMPTY_HINTS` (one sentence per blank pane). Holds no React and no state — like the rest of `lib/`. This is a **content** module, so it is the one place in `lib/` where editing is a copy change rather than a logic change; keep its wording in step with the code it describes (see the 帮助 entry under Conventions).
- `types/assets.d.ts` — ambient `declare module "*.css"` declarations, needed so `import './globals.css'` typechecks.

### Data flow

JSON parsing, formatting, sorting, statistics, tree rendering, and search all happen **client-side**. State is entirely local `useState`/`useMemo` in `JsonTool.tsx`'s default export, and the components under it are controlled — there is no Context, Redux, or Zustand.

**There is exactly one network path, and it is none.** No `fetch`, no `XMLHttpRequest`, no WebSocket, no server route — `app/` has no `api/` directory and `JsonTool.tsx` never calls out. Everything the app does is local. This is a property worth protecting rather than a coincidence: the README tells users the tool is 纯前端、不联网、不往任何地方发数据, so one added `fetch` turns a true statement into a false one. If something seems to need a server, it almost certainly belongs in the browser — parsing, formatting, sorting, folding and search all already are.

Persistence is the only other thing that touches storage, and it is all `localStorage`: `jsontool.history` (records), `jsontool.prefs` (preferences).

**The 保存记录 panel** (reached from the activity bar; renamed from 历史记录 at the user's request, because the name implied *automatic* recording while `pushHistory` has exactly one call site) lives under `localStorage["jsontool.history"]`: an array of `{ id, ts, text }`, newest first, trimmed to `HIST_MAX` entries and `HIST_MAX_CHARS` total characters. The trim is not optional — localStorage's quota is a few MB, and an untrimmed `setItem` throws `QuotaExceededError`, which the surrounding `catch` swallows, so the symptom is "records silently stop saving". Both caps are spelled out in the panel's **empty state** — as the last line of the 保存记录 section in `lib/help.ts`, interpolated from `HIST_MAX` / `fmtBytes(HIST_MAX_CHARS)` so the numbers cannot drift from `pushHistory`'s trimming. Keep it: the caps are otherwise invisible, and a user who watches entries vanish without explanation reads it as a bug. It used to be a separate `.small` line in the JSX *and* a hand-written sentence in the help copy, which said the same thing with different numbers (`2.0 MB` vs what `fmtBytes` actually renders, `2 MB`) — one statement now, sourced from the constants. Note the two caps are independent, and a large document hits the *byte* cap first (measured: 4 × 500 KB entries fill the whole 2 MB budget while the count is still nowhere near 60). **`pushHistory` has exactly one call site: the 保存 button.** There is deliberately **no** auto-recording — not on edits, not on 格式化 / 压缩 / 示例 / Unicode / 转义 / 上传 / 拖入. That was an explicit correction from the user, so do not "improve" it by adding a debounce effect or sprinkling calls into the action handlers; doing so silently fills the list with states nobody asked to keep. Each row is a card with **exactly two lines**: line 1 holds the relative time (`fmtRel` — 刚刚 / N 分钟前 / N 小时前 / N 天前, falling back to an absolute `YYYY/MM/DD HH:mm:ss` past 30 days) on the left and the absolute time · size pushed right via `margin-left: auto` (ellipsised, so a narrow panel cannot overflow); line 2 is the **front** of the text with runs of whitespace collapsed to single spaces (`histPreview`), so a multi-line document still reads on one line. The row's delete button is vertically centred, which is why `.hist-row` is `align-items: center` rather than `flex-start`. Hover and press both highlight the **whole card**, and the press highlight is `.hist-row:has(.hist-main:active)` rather than `.hist-main:active` — highlighting only the inner button lit up a box inset by the card's padding, and dropping the `:has()` makes pressing the delete × light the card up as if you were restoring it. `fmtRel` takes `now` as a parameter instead of reading `Date.now()` internally — that is what lets a 30 s ticker keep "刚刚" from hanging forever on a stale render; the ticker runs **only while the 保存记录 panel is open** (`[rightPanel]` dep), so a closed panel costs nothing. `pushHistory` does **not** dedupe: every 保存 click appends a record, identical content included. The user was explicit — 点保存就一定保存 — and the dedupe this replaced made a second save look like a dead button. So the trim only ever drops *older* entries; the newest one is always kept even if it alone exceeds `HIST_MAX_CHARS`. Clicking a record loads its text into the editor (`restoreHistory`) and confirms with a toast; the panel is strictly read-only, there is no edit affordance, and none should be added. The loader ignores unknown fields, so entries written by older builds (which carried a `label`) still load. **The rename stopped at the user-visible strings — the identifiers still say `history` / `hist*`, on purpose.** `HIST_KEY` holds the literal `"jsontool.history"` and **that string must never change**: it is the localStorage key, so renaming it silently orphans every entry a user has already saved (the loader would find nothing and the panel would come up empty — data still on disk, unreachable). The other identifiers keep the old spelling so the constant name does not contradict its own value; `JsonTool.tsx` carries a comment at the `useState` saying exactly this. If you ever rename them, change the identifiers *and* the CSS class names together, and leave `HIST_KEY`'s value alone.

## Conventions that are easy to get wrong

- **Control characters are written via `String.fromCharCode(...)`**, not as literals — e.g. `const NL = String.fromCharCode(10)`, `BS = String.fromCharCode(92)`. This pattern is deliberate and repeated across `JsonTool.tsx`, `lib/constants.ts`, `lib/text.ts`, and `e2e.cjs`. (`NL2 = NL1 + NL1`, the SSE frame separator, went away with the AI feature — nothing else used it.) Do not "clean these up" into `\n` / `\\` literals unless you have confirmed the file still builds and behaves correctly — the code was authored this way to work around encoding issues.
- **The four-layer editor.** `.editor-back` is a `<pre>` with the plain text; `.editor-front` is a transparent-text `<textarea>` on top of it (it owns the caret, the selection, and all input); `.editor-marks` is a second `<pre>` above both that renders only the search `<mark>` elements; `.editor-nums` is the line-number gutter — numbers plus the fold triangles, on top of everything. The layering exists because a textarea cannot style substrings, so matches have to be drawn in a separate element. **Paint order is the reverse of DOM order and is set by `z-index`** (`.editor-back` `0`, `.editor-marks` `1`, `.editor-front` `2`, `.editor-nums` `3`) — reordering the JSX alone changes nothing. The native selection is deliberately on **top**: the blue then reads as one continuous band, and a matched word inside a selection is tinted olive instead of staying bright yellow. That is a deliberate choice of the user's, made against the opposite arrangement (yellow on top — brighter match, but the yellow punches a hole in the selection and the blue leaks around it). Do not "fix" it back without asking. **Search navigation must not touch the selection or the focus.** The nav effect only scrolls the editor to the active mark; it does *not* call `setSelectionRange` or `focus()`. It used to, and that planted a blue block in the editor on every 「下一个」 while yanking focus out of the search box — the user reads that block as a stray "cursor" and it is not what they want. The current match is indicated by the `.mark.active` ring alone, and the native blue appears only when the user drags or clicks in the editor themselves. Scroll position is synced manually in the textarea's `onScroll` for the `<pre>` layers, and the search-scroll effect must read the active mark from `.editor-marks`, not `.editor-back`. **`.editor-marks .mark` carries a vertical `padding` that is load-bearing:** an inline `<mark>`'s background only covers the font content area (measured 18px at the default 15px font) while both the line box and the native selection band are 24px, so the padding is exactly what makes the two agree. Vertical padding on an inline element does not affect line-box height, so this does not disturb layer alignment — but horizontal padding must stay `0` (it would push text sideways). Scoped to `.editor-marks` so tree marks keep their tight 18px pill. The value is **`0.2em`, not `3px`** — it has to scale with the font-size setting. `0.2em` is still exactly 3px at the default 15px, so the original calibration is untouched; a fixed `3px` would leave the yellow 1px short of the band at 20px. Measured requirement: 12px→2.6, 15px→3.0, 20px→4.5; `0.2em` gives 2.4/3.0/4.0, all within 0.5px. There is **no syntax highlighting** in the editor — it is a single text color; the colored JSON lives in the tree pane only.
- **The four layers must stay metrically identical — everything above rests on this.** They are four independent text layouts that have to agree pixel-for-pixel, and any box-metric difference silently slides the caret and the blue selection away from the visible text. The diagnostic signature is a screenshot where the *yellow marks are aligned but the selection is not* — the marks and the text both come from `<pre>`s, so only the textarea can drift. `scrollbar-gutter: stable` on all four is **load-bearing, not cosmetic**: the textarea is `overflow: auto`, so a long document pops a scrollbar that narrows its content box by 10px, and it then wraps into extra lines (measured: +2 lines on a 60-line document) while the `<pre>`s keep full width. All four share one rule, so `padding-left` is `calc(10px + var(--gutter))` for every one of them — the line-number column is carved out of all four equally, which is why adding it did not disturb the existing alignment. If alignment breaks again, measure `clientWidth` **and** `scrollHeight` across all four first: a `clientWidth` difference is the cause, a `scrollHeight` difference is the symptom. **The `padding-left` values must match to the last decimal** — that check is what caught the `font: inherit` bug below.
- **`font: inherit` in the shared editor rule is load-bearing — do not "simplify" it to `font-size`.** `<pre>` and `<textarea>` carry a UA-default `font-family: monospace`; a `<div>` does not. The line-number gutter is a `<div>`, so splitting `font: inherit` into a bare `font-size` made the gutter inherit the body's font stack while the other three fell back to the UA default. The two resolve to *different* fonts, and `ch` differs by 0.25px between them (measured 8.247px vs 8px) — a metric difference that would eventually put a wrap point in a different place. The rule therefore reads `font: inherit; font-size: var(--editor-font, 15px); line-height: 1.6;` — `inherit` first, size/line-height overridden after. `line-height` is unitless on purpose so it scales with the font-size setting; inheriting it would hand down a frozen pixel value.
- **Line numbers re-render the text once per logical line, and that is deliberate.** `.editor-nums` renders `raw.split(NL1)` as one `<div class="num-line">` each, containing the line's text — which must be **invisible** — plus an absolutely-positioned `.num`. That `color: transparent` lives on `.editor-nums` itself, and **it is not optional**: without it the whole document is painted a second time in `--fg` on top of `.editor-back`. Because the two copies land pixel-identically it looks harmless in isolation, which is exactly why it went unnoticed — the symptom only appears when something is layered *over* the editor (an open dropdown, a hover tooltip), where the white ghost text then draws on top of it and the menu reads as "faded/transparent". The invisible text is there for one reason: it makes each block exactly as tall as the corresponding line is *in the editor*, so a wrapped line pushes the next number down by the right amount. **Continuation rows of a wrapped line get no number** — that is the user's explicit choice (they were shown both this and the no-wrap alternative), so numbers stay 1:1 with JSON's logical lines. Two traps: `.num-line` needs `min-height: 1.6em`, or an empty line's block collapses to 0 and every later number shifts up one row; and `.num` needs `white-space: nowrap; word-break: normal`, because the inherited `word-break: break-word` drops its min-content width to one character while the `right: calc(100% + var(--fold-w) + 12px)` offset makes its available width negative — together those collapse the box to 1ch and two-digit numbers overflow (measured: 1, 10 and 21 all had an 8.3px box). `LINE_NUM_MAX` (20000) skips the gutter entirely above that line count, since the node count is linear in lines; when it trips, `--gutter` is set to `0px` inline so the three real layers get their padding back. The 设置 panel's **行号** switch (`showLineNums`) hides the numbers only — it is deliberately **not** a gutter switch. `foldCol` is computed independently of it (`ranges.size > 0 && lines.length <= LINE_NUM_MAX`), so turning numbers off leaves the fold triangles in place, in a narrow 38px gutter with no number column; otherwise folding would become unreachable. An earlier version coupled the two and the user asked for them split. `LINE_NUM_MAX` still gates both together, since they share the one `.editor-nums` DOM layer and the node count is the same cost.
- **Gutter geometry is all driven by two inline vars**, `--num-ch` (digits, or `0`) and `--fold-w` (`14px` or `0px`), summed in one CSS calc: `--gutter = num-ch * 1ch + fold-w + 4px`. The trailing constant is the *left* margin of the number column (`measured left offset = constant + 2`), so it directly controls how much dead space sits left of the digits. It has been tightened twice at the user's request — `16px` (a two-digit number had 20px of空白 to its left, more than the digits were wide) → `14px` → **`4px`** (6px actual). `num-ch` is the max line number's **real digit count**, with no `Math.max(2, …)` floor: that floor dates from when the left margin was 20px, and with the margin at 6px it only wastes a character — a 7-line document's numbers are all one digit yet reserved two, pushing the left offset from 6px to 14.2px (measured). The two columns are laid out by `right` offsets, not by flow: `.num` sits at `100% + fold-w + 8px` and `.num-fold` at `100% + 8px`, which makes the number's right edge and the fold column's left edge coincide. The 8px gap between the fold column and the text is where `.editor-wrap.guttered::after` draws the 1px separator rule at `- 4px` — on the **wrap**, not on `.editor-nums`, because that layer scrolls and a per-line `.num-line` cannot form one continuous line. The `::after` needs `z-index: 2` (`.editor-back`'s background is opaque) and is gated on the `guttered` class so it disappears with the gutter.
- **z-index tie-breaks are the trap in this layout, and they have bitten twice.** Two pairs that must not tie, because a tie is resolved by DOM order and the editor is always later: (a) `.pane-head` is **5**, not 3 — at 3 it ties with `.editor-nums`, so the `.actions` dropdown menus and the `[data-tip]` tooltips got painted under the gutter, with numbers and triangles drawn on top of the menu. (b) `.topbar` carries **`z-index: 10`** purely to create a stacking context — it used to have none, which left `.searchbar` (z-index 5) in the same context as `.pane-head` (also 5), and since `.main` comes later the 树形视图 panel covered the search pill's hover tooltip as it dropped into the editor area. The budget is: editor layers 0–3, `.pane-head` 5, `.topbar` 10, toasts 60 (fixed). If you add a layer at z-index ≥ 5 inside `.pane`, or anything inside `.topbar`, re-check both pairs.
- **折叠 is a read-only display mode, and that is forced by the architecture, not a shortcut.** A `<textarea>` cannot hide a subset of its own text, so folded lines cannot simply be hidden in place: the lines below would keep their old positions and the whole layer stack would desync. So while `folding` is true the textarea gets `visibility: hidden` (`.editor-wrap.folded .editor-front`) and `.editor-back` alone renders `foldedText`. Consequences to keep in mind, all deliberate: (a) you cannot type while folded — `toggleFold` calls `blur()` so a stale caret cannot sit in an invisible field, and the first click on the body unfolds everything; (b) **`.editor-nums` becomes the scroll driver** (`.folded .editor-nums { overflow: auto; pointer-events: auto }`), because it is the only interactive layer left and it happens to have the same height as the folded text — its `onScroll` pushes `scrollTop` to the other two, guarded on `folding` so the usual textarea→nums direction cannot fight it; (c) search highlights are **not** drawn while folded — the hit offsets are into `raw`, and after renumbering they would land on the wrong lines; the empty `<pre>` stays mounted purely to keep `marksRef` alive for the search-scroll effect. That made search *dead* while folded rather than merely degraded: the counter still ticked but no yellow appeared, and 「下一个」 did nothing because it locates the target via `querySelector(".mark.active")` on an empty layer. So **any search interaction unfolds** — `onChange` (when the query is non-empty), the Enter branch of `onKeyDown`, and `stepNav` all call `unfold()`. `unfold` returns the same `Set` reference when already empty so React bails out, which is what makes calling it unconditionally cheap. Folding is still *allowed* while a query is active (which hides the highlights again), because the next keystroke or 「下一个」 brings them straight back — the alternative (hiding the triangles during a search) is a bigger rule than the user asked for. Two invariants: `.editor-back` and `.editor-nums` must both render from the same `shown` array (any string built independently on one side forks the wrap points and slides the numbers), and **a folded block collapses to exactly one line** — the hidden set is `open+1 .. closeLine` *inclusive*, and the closing line's tail (from `closeCol`, so the bracket plus any trailing comma) is appended to the opening line. `"tags": [` / 2 items / `],` becomes `"tags": […],`, and folding the root block leaves the single row `{…}`. The opening line is the only row that survives, so `hidden` must include the close line; an earlier version kept it and produced two rows, which the user rejected. `closeCol` is why `foldRanges` returns a `{closeLine, closeCol}` pair rather than a bare line number: for a line closing several blocks at once (`  }],`) slicing the whole line would drag in brackets belonging to other blocks. Fold keys are **line numbers**, so any change to `raw` invalidates all of them; an effect drops the whole set, returning the same reference when it is already empty so React skips the extra render on every keystroke.
- **Whole-document replacements go through `replaceAll(text)`, never bare `setRaw`.** It clears the fold set and sets the text in one batch, and the four transforms the user named — 格式化 / 压缩 / Unicode / 转义 — plus 示例 / 清空 / 上传 / 拖入 / 记录恢复 all use it. The `[raw]` effect above is *not* sufficient on its own, for two reasons: (1) when the content is **already** in the target shape (格式化 on already-formatted text, 中文转 Unicode on an ASCII-only document) the transform returns the identical string, `setRaw` bails out, `raw` never changes and the effect never fires — folds would silently survive the button press; (2) the effect runs after render, so it would first paint one frame of the *new* text carrying the *old* fold keys. Batching both updates removes the stale frame. Only the textarea's own `onChange` still calls `setRaw` directly.

That is deliberate (it is what "font size" means in a code editor) and was confirmed with the user. Like 缩进 / Key 排序 / 行号 it **is** persisted now (see the preferences entry under Conventions). The 设置 panel's controls, in DOM order, are **缩进, Key 排序, 字体大小, 行号**. The first three are the custom `Select` component (which renders a `<button class="input sel-btn">`, *not* a `<select>` — see below) and the fourth is a checkbox. Index-based selectors in any test script depend on that order. - **All transient "that worked" feedback goes through `notify()`.** There is exactly one toast stack; the state and every timer live in `JsonTool`, and `components/Toasts.tsx` only draws it. It is rendered as the last child of `.app` (`position: fixed`, so it does not participate in that flex column and needs no portal). Do not add a per-feature flash flag: the four `notify` replaced — `copied` (which was dead code, never rendered), `saved`, `restoredId`, and `JsonNode`'s `flash` — were four independent implementations of the same idea, which is exactly why they are gone. With plain `column` every new message shoved the whole stack upward — the user reported that as an animation bug. Removal is **two-phase**, gated on `TOAST_OUT_MS`, because the exit keyframe collapses `max-height` / `margin-top` / `padding` / `border-width` to 0 alongside the fade; without the collapse the toasts above snap the instant the element leaves the DOM. Two traps: `TOAST_OUT_MS` must match the CSS `toast-out` duration, and the removal timers must live in a ref rather than an effect `cleanup` — cleanup runs on every `toasts` change, and *arriving* messages are exactly such a change, so it would cancel pending removals and strand toasts on screen. `.toast` also needs its `max-height: 60px` + `overflow: hidden` pair, since `max-height: auto` cannot animate to 0. The toast is a small-radius rectangle (8px, one line) with a type icon on the left and an × on the right. **Only the × dismisses it** — the body is deliberately not clickable (`cursor: default`), matching `ElMessage`; it used to be, and that was wrong. Auto-dismiss is `TOAST_MS` = 3000 ms, `ElMessage`'s default `duration`. **Copy confirmations are emitted by `copy()` itself, never by its callers** — it is the only place that knows whether `navigator.clipboard.writeText` actually resolved, and the empty `catch` that used to be there meant the toast said 已复制 while the clipboard had silently refused. `.toast`'s `@keyframes` is the project's only animation and is disabled under `prefers-reduced-motion`. ## The name, and what deliberately did *not* get renamed

The project is **VS Json** — 对标 VS Code, which the UI already was: the topbar, the activity bar, and the settings page's one-block-per-setting layout all follow it. The rename reached `package.json`'s `name` (`vs-json`), `app/layout.tsx`'s metadata, the topbar's brand text and its SVG's `aria-label`, `app/icon.svg`, the README, and this file.

It stopped at two things, both on purpose:

- **The `localStorage` keys.** `jsontool.history` and `jsontool.prefs` keep their values. The identifiers keep the old spelling for the same reason — a constant named `SAVED_KEY` holding `"jsontool.history"` would contradict its own value. See the `HIST_KEY` entry under Data flow.
- **The identifiers generally.** `history` / `hist*` and `PREFS_KEY` are unchanged for the same reason the 保存记录 rename stopped at the user-visible strings.

`dev.log` and the root `shot.png` used to sit in the repo as stale artifacts (a dev-server log naming routes that no longer exist, and a screenshot of a UI two redesigns old); both are gone. `docs/screenshot.png` and `docs/settings.png` are the current README images. Regenerate them by driving a running app rather than editing them by hand, and keep them at **1×** — GitHub renders README images at ~880px wide, so a 2× capture is bytes nobody ever sees.
