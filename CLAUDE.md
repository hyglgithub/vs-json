## Architecture

A single-page **client-side** JSON viewer/formatter, plus one server route that proxies an LLM "organize this JSON" request. All UI text, code comments, and error messages are **Chinese** (`<html lang="zh-CN">`).

**Next.js 15 App Router, React 19, TypeScript `strict: true`.** No Tailwind, no CSS modules, no state library.

- `app/layout.tsx` — server component; sets metadata (`JSON 工具`) and imports `./globals.css`.
- `app/page.tsx` — server component, 5 lines, just renders `<JsonTool />`.
- `components/JsonTool.tsx` — the only `"use client"` module; everything interactive lives here (~960 lines). The right-hand panels are all inline JSX branches on `rightPanel` inside this file, and the activity-bar buttons at the bottom of `.main` switch between them. The activity bar's order is **树形视图 / 保存记录 / AI 整理 / 帮助 / 设置** (帮助 was swapped ahead of 设置 at the user's request) — the 帮助 branch is the `else` fallback of that ternary chain, so adding a panel means adding a branch *before* it. **帮助 is intentionally an empty pane** — a `pane-head` reading 帮助 with an empty `.tree` under it — added as a placeholder for content the user has not written yet; do not fill it in unprompted. The three inline sub-components (`Highlight`, `JsonNode`, and the JSX-returning `toastIcon`) are *still* defined in this file rather than split out — that is deliberate. Only pure, state-free helpers were extracted.
- `lib/` — those extracted helpers, four flat modules. **They contain no React and no component state, and must stay that way.** The seam is "does this function need to see a `useState`?" — if it does, it belongs in `JsonTool.tsx`, not here. Splitting state into a Context/store was considered and rejected: `expanded` / `query` / `activeIndex` genuinely belong to one screen.
  - `lib/constants.ts` — `NL1` / `BS` / `NL2`, `TOAST_MS` / `TOAST_OUT_MS` / `TOAST_MAX`, the `ToastKind` type, `HIST_KEY` / `HIST_MAX` / `HIST_MAX_CHARS`, the `HistoryEntry` type, `SAMPLE`.
  - `lib/json.ts` — the `JsonValue` / `Match` / `FoldRange` types, `isObject` / `joinKey` / `joinIndex` / `valueClass` / `computeStats` / `collectPaths` / `deepSort` / `findMatches` / `foldRanges`. `escapeKey` is deliberately **not** exported — `joinKey` is its only caller. `foldRanges` is a string-aware bracket scan returning `Map<openLine, {closeLine, closeCol}>` for multi-line blocks; it scans the *text* rather than walking the parsed value because the AST carries no line numbers, and folding is a per-line operation. It must skip brackets inside string literals (`{"a": "[{"}`), hence the escape state machine.
  - `lib/text.ts` — `escapeUnicode` / `unescapeUnicode` (a matched pair — keep them adjacent), `escapeText` / `unescapeText`, `reformatJson`.
  - `lib/format.ts` — `fmtTime` / `fmtRel` / `fmtBytes` / `histPreview`.
- `app/api/organize/route.ts` — the only API route.
- `types/assets.d.ts` — ambient `declare module "*.css"` declarations, needed so `import './globals.css'` typechecks.

### Data flow

JSON parsing, formatting, sorting, statistics, tree rendering, and search all happen **client-side** in `JsonTool.tsx`. State is entirely local `useState`/`useMemo` in the default export — there is no Context, Redux, or Zustand.

The single network path: clicking `开始分析` → `POST /api/organize` with `{ endpoint, key, json }` → the route re-emits its own **SSE** frames (`{t:"delta"|"done"|"error"}`) → `organize()` in `JsonTool.tsx` reads the stream via `res.body.getReader()` and appends deltas into `aiOutput`.

The AI endpoint and key are persisted **in the browser** under `localStorage["jsontool.ai"]`; the key is forwarded per-request and never stored server-side.

**The 保存记录 panel** (reached from the activity bar; renamed from 历史记录 at the user's request, because the name implied *automatic* recording while `pushHistory` has exactly one call site) lives under `localStorage["jsontool.history"]`: an array of `{ id, ts, text }`, newest first, trimmed to `HIST_MAX` entries and `HIST_MAX_CHARS` total characters. The trim is not optional — localStorage's quota is a few MB, and an untrimmed `setItem` throws `QuotaExceededError`, which the surrounding `catch` swallows, so the symptom is "records silently stop saving". Both caps are spelled out in the panel's **empty state** (built from `HIST_MAX` / `fmtBytes(HIST_MAX_CHARS)`, so the numbers cannot drift) — keep that line: the caps are otherwise invisible, and a user who watches entries vanish without explanation reads it as a bug. Note the two caps are independent, and a large document hits the *byte* cap first (measured: 4 × 500 KB entries fill the whole 2 MB budget while the count is still nowhere near 60). **`pushHistory` has exactly one call site: the 保存 button.** There is deliberately **no** auto-recording — not on edits, not on 格式化 / 压缩 / 示例 / Unicode / 转义 / 上传 / 拖入. That was an explicit correction from the user, so do not "improve" it by adding a debounce effect or sprinkling calls into the action handlers; doing so silently fills the list with states nobody asked to keep. Each row is a card with **exactly two lines**: line 1 holds the relative time (`fmtRel` — 刚刚 / N 分钟前 / N 小时前 / N 天前, falling back to an absolute `YYYY/MM/DD HH:mm:ss` past 30 days) on the left and the absolute time · size pushed right via `margin-left: auto` (ellipsised, so a narrow panel cannot overflow); line 2 is the **front** of the text with runs of whitespace collapsed to single spaces (`histPreview`), so a multi-line document still reads on one line. The row's delete button is vertically centred, which is why `.hist-row` is `align-items: center` rather than `flex-start`. Hover and press both highlight the **whole card**, and the press highlight is `.hist-row:has(.hist-main:active)` rather than `.hist-main:active` — highlighting only the inner button lit up a box inset by the card's padding, and dropping the `:has()` makes pressing the delete × light the card up as if you were restoring it. `fmtRel` takes `now` as a parameter instead of reading `Date.now()` internally — that is what lets a 30 s ticker keep "刚刚" from hanging forever on a stale render; the ticker runs **only while the 保存记录 panel is open** (`[rightPanel]` dep), so a closed panel costs nothing. `pushHistory` does **not** dedupe: every 保存 click appends a record, identical content included. The user was explicit — 点保存就一定保存 — and the dedupe this replaced made a second save look like a dead button. So the trim only ever drops *older* entries; the newest one is always kept even if it alone exceeds `HIST_MAX_CHARS`. Clicking a record loads its text into the editor (`restoreHistory`) and confirms with a toast; the panel is strictly read-only, there is no edit affordance, and none should be added. The loader ignores unknown fields, so entries written by older builds (which carried a `label`) still load. **The rename stopped at the user-visible strings — the identifiers still say `history` / `hist*`, on purpose.** `HIST_KEY` holds the literal `"jsontool.history"` and **that string must never change**: it is the localStorage key, so renaming it silently orphans every entry a user has already saved (the loader would find nothing and the panel would come up empty — data still on disk, unreachable). The other identifiers keep the old spelling so the constant name does not contradict its own value; `JsonTool.tsx` carries a comment at the `useState` saying exactly this. If you ever rename them, change the identifiers *and* the CSS class names together, and leave `HIST_KEY`'s value alone.

### `/api/organize` (route.ts)

`runtime = "nodejs"`, `dynamic = "force-dynamic"`, `maxDuration = 60` (the upstream is slow — the dev log shows 25s responses). It makes **two** upstream calls to a DeepSeek-compatible service: `POST {base}/api/v0/chat_session/create` (then recursively locates `chat_session.id` in the response), then `POST {base}/api/v0/chat/completion` with the `ORGANIZE_SCHEMA` JSON schema. Input is capped at `MAX_AI_CHARS = 120000`. The final JSON is rendered into Chinese headings (`【概要】/【结构】/【字段含义】/【可疑字段】/【重排建议】`) by `renderResult`.

Config resolution: key from the request body, else `process.env.DEEPSEEK_API_KEY`; endpoint from the request body, else `process.env.DEEPSEEK_ENDPOINT`, else the hardcoded default `http://120.77.200.18:8787`. **That default is duplicated** in `app/api/organize/route.ts:9` and in the component's initial state at `components/JsonTool.tsx:132` — change both together.

## Conventions that are easy to get wrong

- **Control characters are written via `String.fromCharCode(...)`**, not as literals — e.g. `const NL = String.fromCharCode(10)`, `BS = String.fromCharCode(92)`, and `NL2 = NL1 + NL1` for the SSE frame separator. This pattern is deliberate and repeated across `JsonTool.tsx`, `lib/constants.ts`, `lib/text.ts`, `route.ts`, and `e2e.cjs`. Do not "clean these up" into `\n` / `\\` literals unless you have confirmed the file still builds and behaves correctly — the code was authored this way to work around encoding issues.
- **The four-layer editor.** `.editor-back` is a `<pre>` with the plain text; `.editor-front` is a transparent-text `<textarea>` on top of it (it owns the caret, the selection, and all input); `.editor-marks` is a second `<pre>` above both that renders only the search `<mark>` elements; `.editor-nums` is the line-number gutter — numbers plus the fold triangles, on top of everything. The layering exists because a textarea cannot style substrings, so matches have to be drawn in a separate element. **Paint order is the reverse of DOM order and is set by `z-index`** (`.editor-back` `0`, `.editor-marks` `1`, `.editor-front` `2`, `.editor-nums` `3`) — reordering the JSX alone changes nothing. The native selection is deliberately on **top**: the blue then reads as one continuous band, and a matched word inside a selection is tinted olive instead of staying bright yellow. That is a deliberate choice of the user's, made against the opposite arrangement (yellow on top — brighter match, but the yellow punches a hole in the selection and the blue leaks around it). Do not "fix" it back without asking. **Search navigation must not touch the selection or the focus.** The nav effect only scrolls the editor to the active mark; it does *not* call `setSelectionRange` or `focus()`. It used to, and that planted a blue block in the editor on every 「下一个」 while yanking focus out of the search box — the user reads that block as a stray "cursor" and it is not what they want. The current match is indicated by the `.mark.active` ring alone, and the native blue appears only when the user drags or clicks in the editor themselves. Scroll position is synced manually in the textarea's `onScroll` for the `<pre>` layers, and the search-scroll effect must read the active mark from `.editor-marks`, not `.editor-back`. **`.editor-marks .mark` carries a vertical `padding` that is load-bearing:** an inline `<mark>`'s background only covers the font content area (measured 18px at the default 15px font) while both the line box and the native selection band are 24px, so the padding is exactly what makes the two agree. Vertical padding on an inline element does not affect line-box height, so this does not disturb layer alignment — but horizontal padding must stay `0` (it would push text sideways). Scoped to `.editor-marks` so tree marks keep their tight 18px pill. The value is **`0.2em`, not `3px`** — it has to scale with the font-size setting. `0.2em` is still exactly 3px at the default 15px, so the original calibration is untouched; a fixed `3px` would leave the yellow 1px short of the band at 20px. Measured requirement: 12px→2.6, 15px→3.0, 20px→4.5; `0.2em` gives 2.4/3.0/4.0, all within 0.5px. There is **no syntax highlighting** in the editor — it is a single text color; the colored JSON lives in the tree pane only.
- **The four layers must stay metrically identical — everything above rests on this.** They are four independent text layouts that have to agree pixel-for-pixel, and any box-metric difference silently slides the caret and the blue selection away from the visible text. The diagnostic signature is a screenshot where the *yellow marks are aligned but the selection is not* — the marks and the text both come from `<pre>`s, so only the textarea can drift. `scrollbar-gutter: stable` on all four is **load-bearing, not cosmetic**: the textarea is `overflow: auto`, so a long document pops a scrollbar that narrows its content box by 10px, and it then wraps into extra lines (measured: +2 lines on a 60-line document) while the `<pre>`s keep full width. All four share one rule, so `padding-left` is `calc(10px + var(--gutter))` for every one of them — the line-number column is carved out of all four equally, which is why adding it did not disturb the existing alignment. If alignment breaks again, measure `clientWidth` **and** `scrollHeight` across all four first: a `clientWidth` difference is the cause, a `scrollHeight` difference is the symptom. **The `padding-left` values must match to the last decimal** — that check is what caught the `font: inherit` bug below.
- **`font: inherit` in the shared editor rule is load-bearing — do not "simplify" it to `font-size`.** `<pre>` and `<textarea>` carry a UA-default `font-family: monospace`; a `<div>` does not. The line-number gutter is a `<div>`, so splitting `font: inherit` into a bare `font-size` made the gutter inherit the body's font stack while the other three fell back to the UA default. The two resolve to *different* fonts, and `ch` differs by 0.25px between them (measured 8.247px vs 8px) — a metric difference that would eventually put a wrap point in a different place. The rule therefore reads `font: inherit; font-size: var(--editor-font, 15px); line-height: 1.6;` — `inherit` first, size/line-height overridden after. `line-height` is unitless on purpose so it scales with the font-size setting; inheriting it would hand down a frozen pixel value.
- **Line numbers re-render the text once per logical line, and that is deliberate.** `.editor-nums` renders `raw.split(NL1)` as one `<div class="num-line">` each, containing the line's text — which must be **invisible** — plus an absolutely-positioned `.num`. That `color: transparent` lives on `.editor-nums` itself, and **it is not optional**: without it the whole document is painted a second time in `--fg` on top of `.editor-back`. Because the two copies land pixel-identically it looks harmless in isolation, which is exactly why it went unnoticed — the symptom only appears when something is layered *over* the editor (an open dropdown, a hover tooltip), where the white ghost text then draws on top of it and the menu reads as "faded/transparent". The invisible text is there for one reason: it makes each block exactly as tall as the corresponding line is *in the editor*, so a wrapped line pushes the next number down by the right amount. **Continuation rows of a wrapped line get no number** — that is the user's explicit choice (they were shown both this and the no-wrap alternative), so numbers stay 1:1 with JSON's logical lines. Two traps: `.num-line` needs `min-height: 1.6em`, or an empty line's block collapses to 0 and every later number shifts up one row; and `.num` needs `white-space: nowrap; word-break: normal`, because the inherited `word-break: break-word` drops its min-content width to one character while the `right: calc(100% + var(--fold-w) + 12px)` offset makes its available width negative — together those collapse the box to 1ch and two-digit numbers overflow (measured: 1, 10 and 21 all had an 8.3px box). `LINE_NUM_MAX` (20000) skips the gutter entirely above that line count, since the node count is linear in lines; when it trips, `--gutter` is set to `0px` inline so the three real layers get their padding back. The 设置 panel's **行号** switch (`showLineNums`) hides the numbers only — it is deliberately **not** a gutter switch. `foldCol` is computed independently of it (`ranges.size > 0 && lines.length <= LINE_NUM_MAX`), so turning numbers off leaves the fold triangles in place, in a narrow 38px gutter with no number column; otherwise folding would become unreachable. An earlier version coupled the two and the user asked for them split. `LINE_NUM_MAX` still gates both together, since they share the one `.editor-nums` DOM layer and the node count is the same cost.
- **Gutter geometry is all driven by two inline vars**, `--num-ch` (digits, or `0`) and `--fold-w` (`14px` or `0px`), summed in one CSS calc: `--gutter = num-ch * 1ch + fold-w + 4px`. The trailing constant is the *left* margin of the number column (`measured left offset = constant + 2`), so it directly controls how much dead space sits left of the digits. It has been tightened twice at the user's request — `16px` (a two-digit number had 20px of空白 to its left, more than the digits were wide) → `14px` → **`4px`** (6px actual). `num-ch` is the max line number's **real digit count**, with no `Math.max(2, …)` floor: that floor dates from when the left margin was 20px, and with the margin at 6px it only wastes a character — a 7-line document's numbers are all one digit yet reserved two, pushing the left offset from 6px to 14.2px (measured). The two columns are laid out by `right` offsets, not by flow: `.num` sits at `100% + fold-w + 8px` and `.num-fold` at `100% + 8px`, which makes the number's right edge and the fold column's left edge coincide. The 8px gap between the fold column and the text is where `.editor-wrap.guttered::after` draws the 1px separator rule at `- 4px` — on the **wrap**, not on `.editor-nums`, because that layer scrolls and a per-line `.num-line` cannot form one continuous line. The `::after` needs `z-index: 2` (`.editor-back`'s background is opaque) and is gated on the `guttered` class so it disappears with the gutter.
- **z-index tie-breaks are the trap in this layout, and they have bitten twice.** Two pairs that must not tie, because a tie is resolved by DOM order and the editor is always later: (a) `.pane-head` is **5**, not 3 — at 3 it ties with `.editor-nums`, so the `.actions` dropdown menus and the `[data-tip]` tooltips got painted under the gutter, with numbers and triangles drawn on top of the menu. (b) `.topbar` carries **`z-index: 10`** purely to create a stacking context — it used to have none, which left `.searchbar` (z-index 5) in the same context as `.pane-head` (also 5), and since `.main` comes later the 树形视图 panel covered the search pill's hover tooltip as it dropped into the editor area. The budget is: editor layers 0–3, `.pane-head` 5, `.topbar` 10, toasts 60 (fixed). If you add a layer at z-index ≥ 5 inside `.pane`, or anything inside `.topbar`, re-check both pairs.
- **折叠 is a read-only display mode, and that is forced by the architecture, not a shortcut.** A `<textarea>` cannot hide a subset of its own text, so folded lines cannot simply be hidden in place: the lines below would keep their old positions and the whole layer stack would desync. So while `folding` is true the textarea gets `visibility: hidden` (`.editor-wrap.folded .editor-front`) and `.editor-back` alone renders `foldedText`. Consequences to keep in mind, all deliberate: (a) you cannot type while folded — `toggleFold` calls `blur()` so a stale caret cannot sit in an invisible field, and the first click on the body unfolds everything; (b) **`.editor-nums` becomes the scroll driver** (`.folded .editor-nums { overflow: auto; pointer-events: auto }`), because it is the only interactive layer left and it happens to have the same height as the folded text — its `onScroll` pushes `scrollTop` to the other two, guarded on `folding` so the usual textarea→nums direction cannot fight it; (c) search highlights are **not** drawn while folded — the hit offsets are into `raw`, and after renumbering they would land on the wrong lines; the empty `<pre>` stays mounted purely to keep `marksRef` alive for the search-scroll effect. That made search *dead* while folded rather than merely degraded: the counter still ticked but no yellow appeared, and 「下一个」 did nothing because it locates the target via `querySelector(".mark.active")` on an empty layer. So **any search interaction unfolds** — `onChange` (when the query is non-empty), the Enter branch of `onKeyDown`, and `stepNav` all call `unfold()`. `unfold` returns the same `Set` reference when already empty so React bails out, which is what makes calling it unconditionally cheap. Folding is still *allowed* while a query is active (which hides the highlights again), because the next keystroke or 「下一个」 brings them straight back — the alternative (hiding the triangles during a search) is a bigger rule than the user asked for. Two invariants: `.editor-back` and `.editor-nums` must both render from the same `shown` array (any string built independently on one side forks the wrap points and slides the numbers), and **a folded block collapses to exactly one line** — the hidden set is `open+1 .. closeLine` *inclusive*, and the closing line's tail (from `closeCol`, so the bracket plus any trailing comma) is appended to the opening line. `"tags": [` / 2 items / `],` becomes `"tags": […],`, and folding the root block leaves the single row `{…}`. The opening line is the only row that survives, so `hidden` must include the close line; an earlier version kept it and produced two rows, which the user rejected. `closeCol` is why `foldRanges` returns a `{closeLine, closeCol}` pair rather than a bare line number: for a line closing several blocks at once (`  }],`) slicing the whole line would drag in brackets belonging to other blocks. Fold keys are **line numbers**, so any change to `raw` invalidates all of them; an effect drops the whole set, returning the same reference when it is already empty so React skips the extra render on every keystroke.
- **Whole-document replacements go through `replaceAll(text)`, never bare `setRaw`.** It clears the fold set and sets the text in one batch, and the four transforms the user named — 格式化 / 压缩 / Unicode / 转义 — plus 示例 / 清空 / 上传 / 拖入 / 记录恢复 all use it. The `[raw]` effect above is *not* sufficient on its own, for two reasons: (1) when the content is **already** in the target shape (格式化 on already-formatted text, 中文转 Unicode on an ASCII-only document) the transform returns the identical string, `setRaw` bails out, `raw` never changes and the effect never fires — folds would silently survive the button press; (2) the effect runs after render, so it would first paint one frame of the *new* text carrying the *old* fold keys. Batching both updates removes the stale frame. Only the textarea's own `onChange` still calls `setRaw` directly.
- **The 设置 panel's 字体大小 only drives `--editor-font`**, which is set inline on `.editor-wrap`; the right-hand tree and panels keep the 15px `body` font. That is deliberate (it is what "font size" means in a code editor) and was confirmed with the user. Neither it nor 缩进 / 行号 / Key 排序 is persisted to `localStorage` — only the AI endpoint/key are. The 设置 panel's controls, in DOM order, are **缩进, Key 排序, 字体大小, 行号, AI 服务地址, 访问密钥**. The first three are the custom `Select` component (which renders a `<button class="input sel-btn">`, *not* a `<select>` — see below), the fourth is a checkbox, the last two are plain inputs. Index-based selectors in any test script depend on that order. 缩进 / Key 排序 are grouped first because both are 格式化·压缩 options; 字体大小 / 行号 are editor-display preferences. The grouping was reordered at the user's request (Key 排序 moved above 字体大小) — it is not alphabetical or arbitrary.
- **「恢复默认」 resets only the four display preferences, and must not touch the AI fields.** `SETTINGS_DEFAULTS` is the single source for both the `useState` initialisers and the button, so changing a default cannot desync the two. The AI 服务地址 / 访问密钥 are deliberately excluded: they are **credentials the user entered to reach their own service**, not preferences, and a reset button that wipes a key the user would have to go find again is a footgun. 缩进 / Key 排序 / 字体大小 / 行号 are pure preferences where a reset is obviously safe and reversible. It **always** notifies, even when nothing was off-default — same rule as 格式化, since four already-default settings produce no on-screen change and the button would read as dead.
- **下载 writes `json-<YYYYMMDD-HHmmss>.json`** via `fmtFileStamp`, not a fixed `data.json`. The fixed name meant a second download became `data(1).json` and the files were indistinguishable by name.
- **The topbar's right-hand side is deliberately empty.** `等待输入` / `节点·深度·字节` used to sit there via `.topbar-stats { margin-left: auto }`; it now lives *inside* `.brand`, immediately right of the 标题, and the rule is a `2px` margin instead. The user asked for the freed space and said they have another use for it — leave it empty rather than filling it. `.searchbar` is absolutely centred, so moving the stats did not shift it.
- **Two toolbar icons carry meaning that is easy to undo by accident.** 格式化 is `<>` plus a middle slash (`</>`) at the user's request. And 清空 is a **broom**, not the trash can: 清空 means "sweep this pane clean" while the 删除 in 保存记录 means "delete this record", and the two sharing a trash can read as the same action. If you touch those SVGs, keep them distinguishable.
- **Never route text selection through React state.** Selection changes fire on every mousemove of a drag; putting them in `useState` re-renders the whole `JsonTool` component (including every visible tree row) per frame and makes selection feel laggy on large documents. Let the browser draw the selection natively and keep the data in a `<pre>` layer.
- **All transient "that worked" feedback goes through `notify()`.** One toast stack lives in `JsonTool`, rendered as the last child of `.app` (`position: fixed`, so it does not participate in that flex column and needs no portal). Do not add a per-feature flash flag: the four `notify` replaced — `copied` (which was dead code, never rendered), `saved`, `restoredId`, and `JsonNode`'s `flash` — were four independent implementations of the same idea, which is exactly why they are gone. Two details are load-bearing: the id and the timer are created **outside** the `setState` updater (StrictMode double-invokes updaters — the same trap `pushHistory` documents); and the container is `pointer-events: none` with each toast `auto`, or an invisible box in the bottom-right corner eats clicks. **`notify` never dedupes** — every call appends a toast, identical text included. An earlier version collapsed a repeat message into the one already on screen and just pushed its timer out; the user rejected it, because mashing one button then showed a single toast and read as "the button stopped working". `TOAST_MAX` (5) caps the number of **active** (non-leaving) toasts. Overflow is **not** a `slice` — that was the bug behind 消息满了之后老消息应该有个下落动作: slicing dropped the oldest straight out of the array with no exit animation. `notify` only *flags* the oldest active entries `leaving`, which keeps the updater pure (StrictMode double-invokes it), and one effect performs every actual removal, so expiry, the × button and overflow all share a single exit path. The stack is `flex-direction: column-reverse` **on purpose**: toasts are appended and the container is anchored at `bottom: 16px`, so with `column-reverse` a new message lands on **top** and the existing ones do not budge (measured: 0px shift). With plain `column` every new message shoved the whole stack upward — the user reported that as an animation bug. Removal is **two-phase**, gated on `TOAST_OUT_MS`, because the exit keyframe collapses `max-height` / `margin-top` / `padding` / `border-width` to 0 alongside the fade; without the collapse the toasts above snap the instant the element leaves the DOM. Two traps: `TOAST_OUT_MS` must match the CSS `toast-out` duration, and the removal timers must live in a ref rather than an effect `cleanup` — cleanup runs on every `toasts` change, and *arriving* messages are exactly such a change, so it would cancel pending removals and strand toasts on screen. `.toast` also needs its `max-height: 60px` + `overflow: hidden` pair, since `max-height: auto` cannot animate to 0. The toast is a small-radius rectangle (8px, one line) with a type icon on the left and an × on the right. **Only the × dismisses it** — the body is deliberately not clickable (`cursor: default`), matching `ElMessage`; it used to be, and that was wrong. All five kinds — `primary` (default) / `success` / `info` / `warning` / `error` — carry an icon and a tinted background: each kind sets `--tint` + `color` + `border-color` from the existing `--accent` / `--str` / `--muted` / `--num` / `--err` variables (no new palette), and `.toast` layers that tint as a `linear-gradient` over an opaque `--panel2` base — the toast floats above the editor, so a translucent background on its own would let the text underneath show through. Auto-dismiss is `TOAST_MS` = 3000 ms, `ElMessage`'s default `duration`. **Copy confirmations are emitted by `copy()` itself, never by its callers** — it is the only place that knows whether `navigator.clipboard.writeText` actually resolved, and the empty `catch` that used to be there meant the toast said 已复制 while the clipboard had silently refused. `.toast`'s `@keyframes` is the project's only animation and is disabled under `prefers-reduced-motion`. Actions that notify: 复制 / 保存 / 记录恢复 / 树内双击复制 / 格式化 / 压缩 / 清空 / 下载 / 上传 / 拖入 / 恢复默认设置. Deliberately **not** 示例 / Unicode / 转义 / 全展开全折叠 / panel switches — their result is already visible in place, so a bubble on top of it is only noise. The test when adding one: **could the user tell the action did anything?** 格式化 on already-formatted text is the case that forced this rule — nothing on screen changes, so it read as a dead button.
- **Holding 上一个/下一个 repeats.** The step runs in `onPointerDown` (immediate feedback), then a 380 ms pause, then a 60 ms interval, stopped by pointerup / pointerleave / pointercancel. `onClick` steps **only** when `event.detail === 0`: a real pointer click reports `detail >= 1` and was already handled by `pointerdown`, so without that guard a tap advances twice. Scripted clicks (`element.click()`, which is what `e2e.cjs` uses) report `detail === 0` and still step once.
- **`e2e.cjs` depends on the CSS class contract** `.actions` and `.editor-front`, and on exact Chinese button labels. Renaming those classes or buttons silently breaks the harness.
- **Styling** is plain CSS in `app/globals.css` using custom properties (`--bg`, `--panel`, `--accent`, `--str`, …) with short one-line rules. Inline `style` is used only for dynamic values like the splitter width.
- **The 设置 panel follows VS Code's settings layout: one block per setting, stacked title → description → control, all three left-aligned.** The user asked for this explicitly after seeing a VS Code screenshot, replacing an earlier "label column on the left, control on the right" form — that form forced a long label to wrap and pushed the control to the far edge of the panel, away from its own title, which made the list hard to read top-to-bottom. Supporting details: `.setting` carries its own vertical padding instead of the container using `gap`, so the hit area equals the visual block; the wrapper is a `<label>` (clicking the title focuses the control) *except* for 行号, which is a real `<input type="checkbox">` and needs its own inner label instead of a nested one; the checkbox is drawn from scratch (`appearance: none` + a data-URI tick) because a native checkbox renders light-on-dark. Controls are `width: 100%` but **capped at `max-width: 320px`** — panel width is whatever the user dragged the splitter to, and a dropdown reading 「2 空格」 stretched to 800px is absurd (measured before the cap: 804px). The background is **transparent**, showing `.pane`'s `--bg`: it used to paint `--panel2` and read as "not one of them" next to 树形视图 / 保存记录 / AI, which all sit on `--bg`.
- **The 设置 dropdowns are a custom `Select` component, not `<select>`, and the reason is the popup.** A native `<select>`'s list is drawn by the OS: the selected row gets a solid system-blue highlight and every corner is square, none of which CSS can reach. The user compared it against the app's own 格式化 / Unicode / 转义 menus and asked for those instead. So `Select` is a `<button class="input sel-btn">` (it borrows `.input`, so the *closed* control is pixel-identical to the text inputs — same 320×32 box, same 8px radius, same chevron) plus the shared `.menu` / `.menu-item` classes. Three details are load-bearing:
  - **The popup is `position: fixed`, not `absolute`.** `.settings` is an `overflow: auto` scroll container, and an absolutely-positioned popup cannot escape its clip — measured in a short window: menu bottom 597 cut at the panel's 418. Fixed positioning leaves the clip entirely, which then costs two things this component has to do itself: close on scroll (`scroll` doesn't bubble — the listener must be capture-phase) and flip above the button when there is no room below.
  - **The flip is measured in `useLayoutEffect`, not `useEffect`.** It runs before paint, so "render below, then flip above" never flashes on screen.
  - **The list options are force-matched to the control's 32px height** via `.sel-menu .menu-item { padding: 4px 10px }` — the shared `.menu-item` uses `7px` (→ 38px), which is 6px taller than the `.input` box sitting directly above it and reads as two mismatched blocks once the list opens. Scoped to `.sel-menu` on purpose: the toolbar's 格式化 / Unicode / 转义 menus have no control above them to match, so they keep the roomier original.
  - **Rule order matters in `globals.css` for `.menu-item.on` / `.menu-item.hi`.** They are `(0,2,0)` like the global `.menu-item:hover`, so they must come *after* it — placed earlier, hovering the current value snaps its text back to `--fg` and you can no longer see which option is selected. `.hi` sets background only; `.on` sets colour only, so the selected row keeps its accent text while hovered.
- **The `.input` chevron is a hardcoded-colour inline SVG data URI, and that is the one place a colour is duplicated outside `:root`.** `<select>` gets `appearance: none` because the native arrow renders differently per platform and ignores the theme; a `::after` triangle is not an option (replaced elements have no pseudo-elements), so the arrow has to be a `background-image`, and a data URI cannot see `currentColor`. It is `#8b93a7` = `--muted`. **If the palette ever changes, sync that literal.** The popup list itself stays OS-drawn and cannot be styled — `:root { color-scheme: dark }` is what keeps it from being a white flash, so do not remove that.
- **Imports are relative** (`../components/JsonTool`), even though the `@/*` alias is configured in `tsconfig.json`. Match the surrounding style.
- User-facing strings and API error messages are Chinese (`"请求体不是合法 JSON"`, `"缺少 DeepSeek 服务 key"`). Keep new ones Chinese.
